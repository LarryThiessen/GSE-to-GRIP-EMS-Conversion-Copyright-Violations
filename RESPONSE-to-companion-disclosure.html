Response · GSE Companion “disclosure” & video

Setting the record straight

A factual, verifiable response to the recent “GSE Companion” disclosure and video. Every technical claim below can be checked against the exact files and hashes the discloser published — we encourage you to verify it yourself.

Read before publishing — for Tim

This is a draft grounded in verification, but two factual specifics are your knowledge to confirm, not something anyone should take from an outside analysis: (1) that the access‑policy enforce flag was never set true, and (2) that the diagnostic‑upload path was never used to pull a user’s files. The code and the discloser’s own captures point that way, but you are the authority. Confirm both before this goes public — the other side has the source and will check.

01The short version

  • Nobody’s data was deleted. The “delete” routine was gated behind a server flag (enforce) that was off on every date the discloser himself recorded it. It never ran. In the current build it is removed entirely.
  • The GSE addon is free. Full class sets are public and free on CurseForge. No addon feature is sold.
  • No one was “surveilled and banned” for using another addon. Specific individuals were removed from community Discords by human admins for a documented reason.
  • One point is fair, and we’re acting on it (see §06): a diagnostic file‑upload path should be tightened. That’s the right response — not denial.

03“GSE deletes your data”   Did not happen

This is the headline of the video, and it is the claim with the least support — from the discloser’s own evidence.

The cleanup routine only ran under one condition: restricted && enforce. The enforce value comes from the server (GET /settings/access-policy). The discloser captured that endpoint on three separate dates and committed the results to his repo:

From the discloser’s own repo (evidence/live_access_policy_*.json)
2026-06-20   { "enforce": false, ... }
2026-06-21   { "enforce": false, ..., "integrity":"verified" }
2026-07-09   { "enforce": false, ..., "integrity":"verified" }

enforce was false the entire time. The switch that would arm the cleanup was never flipped. The routine never executed against anyone.

Two further facts confirm it:

  • In the current shipping build (0.4.22), that hardcoded cleanup no longer exists. enforce is fetched and shown in the app’s status only; it triggers nothing.
  • It was, by design, a canary — dormant code meant to reveal who was quietly dissecting the Companion app. The people who found it and raised the alarm are the people who were taking it apart.

So “could delete your data” is technically about code that was present; “deleted your data” never occurred, and the discloser’s own files prove the trigger was off.

04“GSE is a paywall / breaks the EULA”   Misframed

  • The GSE addon is 100% free — the entire addon, on CurseForge. No feature is locked behind payment in the addon.
  • GSE.Tools is free and takes no money. It runs no Patreon of its own and profits from none.
  • Individual creators may optionally link their own Patreon to gate their own premium sequences — exactly like Patreon anywhere else. The full class sets are public and free. That is a creator’s choice about a creator’s content, on a free platform — not GSE selling addon functionality.

05“GSE surveils and bans people for using GRIP”   Misframed

There is no automated “detect‑and‑ban” dragnet. Specific people were removed from community Discords by human admins, for a documented reason: they organised to scrape creators’ All‑Rights‑Reserved sequences, convert them, strip the ownership identifier, and redistribute them. That is moderation of a specific, evidenced pattern of conduct — not surveillance of ordinary users.

06Where the disclosure has a fair point — and what has changed since

Credibility means conceding what’s real. In the build the disclosure examined (0.4.22) there was a diagnostic file‑gathering path that could, on a server request, read files from the WoW folders — including addon error logs — and upload them. Unlike the delete routine, it was not behind the enforce switch. We found no evidence it was ever used to pull anyone’s files. Rather than argue the point, here is precisely what is different in the current build:

What changed, as of 0.4.26
  • Addon error logs are no longer collected. The request for them is discarded before any file is gathered, so the BugGrabber/BugSack logs cannot be pulled even if something asks for them.
  • Credentials are stripped from anything sent. Access tokens and session data are removed from diagnostic payloads.
  • Reads are limited to GSE’s own files in the always‑on path — not other addons’, not arbitrary server‑named paths.
  • A file request now raises a visible notification rather than happening quietly.
Still outstanding — stated plainly

Each individual request is not yet cryptographically signed. It requires an authenticated session and a freshly‑issued token, but not the per‑request ed25519 signature the destructive path already uses. That hardening is still to come. We would rather publish that here than have someone else point it out.

Before someone “catches” us on this — we’ll say it first

The error‑log reading code is still present in the file. Anyone running a strings scan over the app will find the pattern /^!?Bug(Grabber|Sack)\.lua$/i and can claim nothing changed. Here is the honest distinction: being present is not being reachable. The request handler now discards the errorlogs request before any file is gathered, so that code cannot be triggered by a server request. You can confirm it yourself — find .delete("errorlogs") in out/main/index.js. We would rather point at it than have it presented as a discovery.

Everything in this section is checkable in the shipped application, not a promise about intentions.
